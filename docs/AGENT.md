# Agent 架构评审与后续研究方向

> 记录当前多 Agent 的拓扑、每个角色的边界、已知局限，以及从 Agent 技术角度看值得做的下一步。
> 配套：`docs/SPEC.md`（规格）、`docs/INTRO.md`（项目介绍）。

## 一、当前拓扑：四个窄 Agent + 一圈确定性护栏

```
                     ┌──────────────┐
   玩家行动 ─────────▶│ 叙事 Narrator │──流式正文──▶ 审计（死角色/未知人名/字数）
                     └──────────────┘                     │
                                                          ▼
   ┌──────────────┐   并行    ┌──────────────┐     提交 Scene(committed)
   │ 档案员 Archive│◀─────────│ 收线 Triage   │◀──── 正文 + 未收清单
   └──────────────┘           └──────────────┘
          │ ops + evidence            │ resolved 编号 + 位置
          ▼                           ▼
   domain/patch 校验与应用 ──▶ canon / clues / facts（确定性，不信任模型）
```

| 角色 | 输入 | 输出 | 权限 |
|---|---|---|---|
| 叙事 | 预算内上下文 + 行动 + 判定结果 | 正文 + 4 个带意图的选项 | 只写正文，不写档案 |
| 档案员 | 正文 + canon 表 + 未收线索编号 | ops（带 evidence） | 只能通过补丁改档案，且逐条校验 |
| 收线校对 | 正文 + 未收问题 | 回答了哪几条 + 原句 + 结束时地点 | 只能收线/改位置 |
| 生成 | 世界、目标、人物、最近三幕 | 事件/秘密草稿 | 只出草稿，用户确认才落库 |

**关键设计**：模型永远不直接改状态。它只能提交"提议"，由 `domain/patch` 做证据校验、
上限、去重、幂等，再由仓储落库。这把"幻觉入库"从概率问题变成可检测的布尔问题。

## 二、这套架构解决了什么

1. **上下文可控**：分区预算 + 裁剪顺序，prompt 长度不随幕数爆炸。
2. **失败可隔离**：抽取失败不阻塞下一幕；收线失败只是这次没收；生成失败只提示。
3. **可测**：每个 Agent 的输入输出都是纯数据，prompt 可单测、指标可回归。
4. **可换模型**：Agent 只依赖 OpenAI 兼容协议，换 DeepSeek / 百炼不改业务代码。

## 三、已知局限（按影响排序）

| 局限 | 表现 | 为什么现在没做 |
|---|---|---|
| 单遍抽取，无核验 | 档案员说"他死了"，没有第二个角色复核 | 加一轮复核会把每幕成本翻倍；先用 evidence 校验挡住最脏的部分 |
| 没有全局规划 | 25 幕的走向靠阶段规则与固定事件，不是真的"先有大纲" | 大纲 Agent 需要先有稳定 canon，否则计划天天改 |
| 收线判定是二值的 | 只能答"答了/没答"，没有置信度与"接近答案"的中间态 | 中间态会让"收线"变成模糊操作，宁可保守 |
| 记忆不压缩 | `arc`/`place.events` 满了按优先级淘汰，没有真正的合并 | 压缩会改写因果，错误会复利（见 SPEC §5.10.1） |
| 没有工具调用 | 入梦只有四个动词，不能"拿起/交给/使用" | 工具调用要先把物品与位置建模，属于完整版入梦 |
| 评测样本小 | eval 20 例、试玩 3 个空间 | 标注成本高；先用真实翻车场景覆盖高频错误 |

## 四、值得做的研究方向

### 1. 轨迹级偏好优化（最值得做）

现在的训练信号只有"单步对不对"。真正要优化的是**一整局的连贯性**：
人物没有 OOC、伏笔有回收、结局不仓促。做法：

- 用 live harness 批量采样轨迹（同一空间、不同随机种子）；
- 用规则指标（重复率、收线率、阶段推进）自动打标，再用 LLM judge 做粗排；
- 在"档案员/叙事"上做 DPO 或 GRPO，奖励 = 轨迹级一致性，而不是单幕文采。

风险：奖励稀疏、方差大。先从"档案员 ops 的接受率"这种密集中间信号起步更稳。

### 2. 生成—核验—修订闭环

把叙事拆成 draft → verify → revise：核验器只做一件事——把正文里的**断言**抽出来，
逐条对照 canon 与事实账，输出冲突列表；冲突则带着"哪句和哪条设定矛盾"重写一次。
这比"让模型自己注意一致性"可靠得多，代价是每幕多一次短调用。

### 3. 分层规划：从"阶段规则"到"幕群大纲"

当前阶段是纯函数（按幕数 + 目标状态推导）。下一步可以让规划 Agent 每 5 幕产出一份
"幕群大纲"（3–5 个 beat），叙事只负责把 beat 写成正文。关键是**大纲要可撤销**：
它是一份带版本的文档，不是塞进 prompt 的一段话。

### 4. 检索从关键词走向混合

关键词召回只能救"名字/物件再也没被提到"。同义表达（"那封信" ↔ "一页泛黄的纸"）
需要向量。做法：浏览器侧 bge-small-zh + 关键词加权融合，模型下载失败 1.5s 内降级。
门槛是包体与首屏，不是效果。

### 5. 工具调用：让入梦真正能"动手"

给入梦加 4 个工具：`move(to)` / `take(item)` / `give(item, to)` / `talk(to, topic)`。
这要求先建物品表与位置图，并且明确"入梦的改变要不要写回主线"——
建议：不写回，除非玩家显式"把这件事带回故事里"。

### 6. 记忆整合（episodic → semantic）

把"第 3 幕他提过一封信"整合成"他一直在找一封信"，需要带 provenance 的合并：
每条整合后的记忆保留来源幕号，可追溯、可回滚。没有 provenance 的压缩不要做。

### 7. 评测：从指标到 rubric

现在客观四项 + 人工评级。下一步把主观项 rubric 化（开场吸引力/中段推进/结局收束/选项有后果），
用同一批种子跑 LLM judge，做**趋势**而不是门禁；同时保留人工抽检 10%。

### 8. 成本与延迟路由

档案员、收线校对这类结构化任务可以用小模型（qwen-turbo / deepseek-chat）；
只有结局与关键转折用大模型。路由依据是"任务类型 + 剩余预算"，不是"猜难度"。

## 五、不建议现在做的

- **让 Agent 互相自由对话**：没有明确收益，成本与不可控性都上升；
- **上向量数据库 / 图数据库**：当前数据量在 IndexedDB 里够用，引入外部依赖会让部署变复杂；
- **自动批量生图/配音**：额度会被一次点击吃光，且缓存失效逻辑没做之前必然重复扣费。
